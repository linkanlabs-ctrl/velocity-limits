# bench/limiter_compare.py, 2026-11-02, WSL2 on the i7-13700H laptop (on AC power).
# Rate limits across worker processes on one server: today's free options and velocity_limits 0.1.0.
# Reading:
#  - limits (under Flask-Limiter and slowapi) on memory: 3.3 us per check, but every worker keeps its own
#    count, so 4 workers let through 4x the limit.
#  - limits on Redis: correct, 178 us per check here (redis-py round trip; Redis's own C client needs
#    63-79 us p50 on this WSL2 loopback, so expect roughly 50-100 us on a native Linux server). Needs a Redis
#    server, which tops out at 18.7k checks/s for 8 workers here.
#  - limits on velocity_limits: correct, 1.7 us per check (100x Redis here; the bare table call is 129 ns, the
#    rest is the limits library itself), and 4.1 M checks/s for 8 workers, 218x Redis.
#  - pyrate-limiter's SQLite bucket with a file lock: 318 us per check, and in non-blocking mode a busy lock
#    returns False exactly like "over the limit" (pyrate_limiter/limiter.py, try_acquire catches TimeoutError),
#    so 4 workers got only 494-607 of the 1000 allowed requests across two runs. With filelock 4.x (current,
#    4.2.6) the same call raises TypeError: pyrate passes acquire(False) and filelock 4 rejects a bool timeout.
#    Runs below use filelock 3.32.7.
# Absolute numbers on this laptop move 10-30% between runs (first run of this script, before velocity_limits
# existed: limits-memory 3.6 us, limits-redis 210 us, pyrate 400 us and 494 allowed).
